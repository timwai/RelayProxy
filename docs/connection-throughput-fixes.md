# 连接后吞吐波动修复

本轮针对 Windows、`relay_quic`、默认 BBR、传输策略自动（QUIC/TCP）的反馈，修复代码审查中确认的 9 处缺陷。具体运行环境仍需通过 Windows 实机复测验证效果。

传输策略 Auto 在建立连接时让 QUIC 先尝试 250 ms，再与 TCP 竞争，采用先成功的连接；连接建立后复用当前会话。下面的修复处理数据传输、请求回退和统计中的问题。

| 缺陷 | 修复后的行为 | 回归覆盖 |
| --- | --- | --- |
| BBR 把 quic-go 的发送后 inflight 当成发送前值，丢失首包采样、重复累计当前包，并在空闲后误触发 ProbeRTT | 还原发送前 inflight，正确识别有数据发送的空闲恢复 | 首包带宽采样、采样 inflight、空闲恢复、纯 ACK |
| Windows 服务等待下一次抓包才读取异步 UDP 注入 | 命名管道两端使用 overlapped IO，抓包与注入独立推进 | 无新抓包时注入、断开清理、Windows 原生命名管道测试 |
| 每个出站 UDP 包在抓包循环同步查进程表 | 独立分类队列查询，成功结果按五元组缓存 250 ms，每分片最多 256 条；到期刷新，查询失败不沿用旧身份 | 连续 UDP 包复用、慢查询期间 TCP 继续、端点复用与查询失败、自身隧道 UDP 旁路 |
| 单条直连请求超时导致共享直连会话被关闭 | 对仍存活的共享会话，仅当前请求回退；结合请求上下文判断被包装成“连接已关闭”的超时 | 真实 QUIC 会话中慢请求回退后，既有连接继续传输 |
| 续传端收到 FIN 后退出读循环，反向 ACK 无法处理 | FIN 结束接收数据方向，继续读取 ACK 和检测传输断开 | 半关闭后的反向大流量、直连恢复到 relay_quic 后下载完整 1 MiB |
| 固定的 256/512 KiB 续传窗口在较高 RTT 下限制吞吐 | 桌面、Android、出口和协议默认值统一为每方向最多 8 MiB | 100 ms 延迟 ACK 下的 4 MiB 传输，以及显式小窗口的背压 |
| DNS 合并查询继承首个请求的取消，污染其他等待者 | 各等待者独立取消，共享查询最长 15 秒；最后一个等待者离开即取消并移除查询 | 首个请求取消、全部取消清理、新请求不加入废弃查询 |
| 上游代理目标 IP 串行握手，首个失速地址耗尽总超时 | 对已解析且经过 ACL 检查的地址错开 250 ms 竞争；取消失败握手并释放连接 | HTTP CONNECT 和 SOCKS5 的 IPv6 失速、IPv4 成功、败者关闭、胜者仍可传输 |
| 小流量累计到 Snapshot/Finish 才按当前时间记速率 | 按实际传输时间写入速率桶，独立速率锁避免等待连接列表排序，遗漏列表的连接仍计入总速率 | 空闲后首次读取、结束连接、超出展示容量的流量 |

续传缓冲按实际未确认数据分配，不会在创建连接时预分配 8 MiB；每条发送方向始终受窗口限制。高并发且对端不确认时的最大内存占用会高于旧窗口。显式设置的较小 replay limit 继续生效。两端均更新后才能同时解除双向旧窗口的限制。

Windows 服务管道协议升级为 v5，以便区分旧的同步服务。更新 Windows Agent 后，需要同步更新 Network Service，可使用界面中的“安装/修复”。UDP 分类和转发使用各自的队列，避免正在等待隧道拨号的转发任务阻塞隧道自身的 UDP 旁路。Linux 依赖同步 verdict 的捕获设备继续在 Finalize 前完成分类。

```sh

go test -race ./internal/congestion/... ./internal/p2p/resume ./internal/traffic ./agent/client ./agent/exit ./agent/divert
go test -race ./agent/app ./mobile/androidcore ./agent/routing ./internal/tunnel ./server/gateway ./server/browser_sync
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go test -c -o /tmp/relayproxy-divert-fixed.test.exe ./agent/divert
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build ./agent/app/... ./agent/client/... ./agent/exit/...
```

本地验证环境为 macOS arm64、Go 1.27.1。Windows 命名管道和系统进程查询的原生测试需在 Windows 上执行；交叉编译只验证编译兼容性。

全仓验证还复现了未修改版本中的浏览器同步大帧测试互等：服务端发送完大帧才确认，测试先等确认再读取接收端，小发送缓冲会使两边互等。测试现先读取接收端再验证确认，继续检查原有的大帧传输与签名校验。

## 中继绕行保护与 RDP 路径展示

针对“透明代理启用后连中继也不可用”，绕行地址现在同时包含已认证连接的实际远端 IP 和启用前的 DNS 结果；每次中继会话更换都重新安装捕获规则。中继数据包在进程归属查询、DNS 接管及 UDP 队列之前直接绕行，避免进程查询失败或队列拥塞让隧道依赖自身代理。回归测试覆盖 DNS 结果与实际连接 IP 不同、IPv4/IPv6 切换、分类队列满和默认拒绝规则。

中继不可用时暂停接管，认证恢复后重新启动。启动期间会话被替换时释放旧捕获，避免留下过期绕行规则。Windows 直接捕获在等待工作协程前关闭 WinDivert 句柄，停止接管时清理系统 DNS 缓存，避免已缓存的 FakeIP 影响正常联网。服务捕获的完成通知失败也会释放接管，不再停留在等待下一包的状态。

概览明确区分代理出口可用路径与 RDP 实际 TCP/UDP 路径。RDP 按最终交给转发器的连接记录路径，竞速落败的直连成功不再覆盖 Relay 状态；未发起客户端流量时显示等待，UDP 关联替换或关闭时同步更新路径。并行 TCP 通道使用不同路径时分别显示。公网直连标签兼容协议中的 `public_direct_quic`。

新增验证包括接管暂停后重启、启动时失去就绪状态、完成通知失败、RDP TCP 通道清理、UDP 关联替换、落败直连关闭，以及前端路径范围与优先级测试。Windows 驱动、命名管道及 DNS 缓存清理仍需 Windows 实机验证。

## Windows 整机联网恢复保护

Network Service 对已经捕获、正在交给 Agent 处理的单个数据包设置 5 秒期限，覆盖管道写入和完成确认。超过期限时先关闭 WinDivert 释放系统流量，再关闭管道；没有捕获包时不计时，正常空闲不会触发重置。握手读写也有期限，防止客户端在 Ready 阶段停止读取时占住捕获。管理员直接捕获模式同样对包处理设置期限，即使进程归属查询卡住，仍先释放设备并执行 DNS 清理，再等待工作协程退出。计时器在会话内复用，避免逐包创建新的计时器。

服务在捕获会话结束时清理 Windows DNS 缓存，覆盖 Agent 强制结束、管道断开和超时释放；服务启动时也清理一次，以处理服务自身崩溃后由 SCM 重启的情况。浏览器和其他应用的私有缓存不能通过 Windows DNS API 统一清除，缓存的 FakeIP 仍可能需要等待失效或由应用重新解析，已有代理连接需要重新建立。

透明代理的随机 TCP 监听端口入站规则现在同时限定实际 Agent 程序。服务从命名管道查询客户端 PID 与可执行文件路径，不使用客户端自行声明的路径，避免只按端口放行所有程序。

DNS 高级设置新增“本地 DNS 域名例外”，配置字段为 `routing.dns_direct_domains`。例如 `["corp.example"]` 仅允许 `corp.example` 及其子域名通过原定本地解析器查询，支持 UDP 和同一 TCP DNS 会话中按查询分流；普通域名仍使用原有加密 DNS/FakeIP 路径。配置默认留空，不会因为解析器地址属于内网、应用走 DIRECT、或加密 DNS 出口失败而自动使用明文 DNS。DNS 例外不改变应用连接的路由，需要另行配置对应的 DIRECT 规则。

独立的 `dns-killswitch-windows.ps1` 创建持久 DNS 阻断规则。这些规则会阻止本地 DNS 例外，应由启用该功能的用户明确停用；Agent 不会擅自撤销用户配置的防泄漏规则。系统 DNS 自动模式需要可用的加密 DNS 出口，出口不可用时继续明确失败，诊断页的“检测 DNS 上游”可定位此类故障。

新增测试覆盖活着但不读管道的客户端、丢失完成确认、长时间空闲、阻塞进程查询期间释放捕获、DNS 例外边界、例外热更新、UDP 原解析器与域名关联、混合 TCP DNS 查询，以及 GUI 配置保存/清空。Windows 专用测试另覆盖实际进程路径查询；需在 Windows 上执行，交叉编译不等于驱动及系统 DNS 恢复验收。
